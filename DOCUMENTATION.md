# INVESTIGATION 001 — Технічна документація (v3.1, станом на поточний код)

Ця документація описує проєкт **таким, яким він є в коді**, а не початковий задум. Розбіжності з попереднім README винесено в розділ 11.

---

## 1. Огляд

Веброзслідування у стилі ретро-термінала. Гравець — аналітик кіберкорпорації, доводить гіпотези дедуктивним методом (резолюція пропозиційної логіки) на базі згенерованих або заготовлених справ.

**Стек:**
- Бекенд: Flask (`app.py`), Python
- Фронтенд: один статичний `index.html` зі стилізацією під термінал, спілкується з бекендом через `POST /api/command`
- Стан: зберігається в оперативній пам'яті сервера (`active_sessions`), профілі — у `data/players.json`

---

## 2. Архітектура

```
Браузер (index.html)
   │  POST /api/command  { command, username }
   ▼
Flask app.py
   ├── player.py        — профіль, пароль, ранг
   ├── cases.py         — завантаження стартової справи з JSON
   ├── case_generator.py— процедурна генерація нових справ
   ├── game.py           — GameSession: KB конкретної справи
   └── logic/
        ├── parser.py    — рядок → AST формули
        ├── cnf.py       — AST → КНФ → множина клауз
        ├── models.py    — Literal, Clause, вузли AST
        └── resolution.py— метод резолюції, дерево виведення
```

Кожен активний гравець — окремий запис у `active_sessions[username]` з полями `profile`, `session`, `state`, `last_tree`, `password_attempts`. Стан губиться при перезапуску сервера (не персистентний, на відміну від профілю).

## 3. Реєстрація та автентифікація

Логін відбувається у два кроки просто в термінальному інтерфейсі:

1. Гравець вводить ім'я.
2. Гравець вводить пароль.

Поведінка на кроці пароля:

| Ситуація | Що відбувається |
|---|---|
| Профіль новий (`password_hash` порожній) | Пароль хешується SHA-256 і зберігається, профіль створюється, видається стартова справа |
| Профіль існує, пароль вірний | Вхід, лічильник невдалих спроб скидається, завантажується справа (стартова або нова процедурна) |
| Профіль існує, пароль невірний | Лічильник спроб `+1`, лишок спроб показується гравцю |
| 3-тя невдала спроба | Нікнейм додається до `locked_usernames` **назавжди** (до перезапуску сервера), сесія видаляється, термінал у клієнті блокується (`isLocked = true`, поле вводу вимикається) |

Паролі зберігаються як SHA-256 хеш у `data/players.json`. Солі немає — для навчального проєкту прийнятно, для продакшену недостатньо.

## 4. Профіль і ранги

`player.py`, `PlayerProfile`:

| Поле | Призначення |
|---|---|
| `name` | Унікальний ключ гравця |
| `password_hash` | SHA-256 пароля |
| `solved_count` | Кількість доведених гіпотез |
| `total_score` | Бали (+10 за кожне успішне доведення) |
| `current_level` | Синхронізується з `get_rank()` при кожному завантаженні/збереженні — не є незалежним станом |

Ранг обчислюється з `solved_count`:

| Ранг | Умова |
|---|---|
| Junior Investigator | `solved_count < 5` |
| Middle Investigator | `5 ≤ solved_count < 10` |
| Senior Investigator | `solved_count ≥ 10` |

Ранг визначає, які рівні складності справ гравець може обирати вручну (розділ 8).

## 5. Структура справи (Case)

Формат, спільний для `data/cases.json` і результату `generate_case()`:

```json
{
  "id": 404,
  "title": "СПРАВА 001: НІЧНИЙ ІНЦИДЕНТ У СЕРВЕРНІЙ",
  "mode": "Доведення",
  "level": "Новачок",
  "description": "текст-легенда справи",
  "legend": { "A": "пояснення змінної A", "B": "..." },
  "axioms": ["(A v B)", "(B -> S)", "~A"],
  "target_hypothesis": "~V"
}
```

Стартова справа `id: 404` завжди видається гравцю зі `solved_count == 0` (`CaseLoader.get_starter_case`). Для всіх інших випадків генерується нова справа через `case_generator.generate_case()`.

## 6. Логічне ядро (`logic/`)

- **`parser.py`** — рекурсивний спуск. Токенізатор трактує велику латинську літеру (+ необов'язкові цифри) як змінну, а `~ & v -> <->` — як оператори. Малі літери, крім `v`, не підтримуються.
- **`cnf.py`** — усунення `->`/`<->`, закони де Моргана, дистрибутивність `v` над `&`, розбиття кон'юнкції на множину клауз (`Clause`).
- **`resolution.py`**:
  - `prove(kb, hypothesis)` — додає заперечення гіпотези до KB, послідовно резолює пари клауз, поки не знайде порожню клаузу (`PROVED`) або не вичерпає нові резолюти (`UNDETERMINED`). Веде `parent_map` для відновлення дерева виведення.
  - `is_minimal_inconsistent(kb)` — перевіряє, чи набір клауз несумісний і чи є мінімальним. **Наразі не викликається жодним ігровим модулем** (див. розділ 11).

## 7. Процедурна генерація справ (`case_generator.py`)

Ключова гарантія: KB завжди узгоджена, а гіпотеза завжди доводна.

**Алгоритм:**
1. Обрати рівень → кількість змінних `n` і кількість «хибних слідів» (`LEVELS`).
2. Обрати 3 персонажі з пулу `PEOPLE`, кожному приписати частину подій (`PERSON_EVENTS`) або взяти системну подію (`SYSTEM_EVENTS`).
3. Задати приховану модель світу — випадкове істинне/хибне значення для кожної змінної.
4. Побудувати ланцюжок істинних літералів `l0 → l1 → … → H` довжиною, залежною від рівня, у формі `A -> B`, `~B -> ~A` або `~A v B` (випадково).
5. Стартовий факт ланцюжка іноді оформлюється як `F v l0` + `~F` (як у справі №404), а не прямим фактом.
6. Додати хибні сліди — узгоджені, але не потрібні для доведення твердження.
7. **Гарантія покриття**: будь-яка змінна легенди, що не потрапила в жодну аксіому, додається окремим фактом (`true_lit(v)`).
8. Перевірити результат реальним викликом `prove()` — якщо не `PROVED`, генерація вважається некоректною (`assert`).
9. Скласти опис у стилі «місце + інцидент + хто був присутній + кого підозрюють + що довести», без розкриття аксіом у тексті.

Рівні прив'язані до назв рангів гравця (`Junior/Middle/Senior Investigator`), а не до українських назв із раннього дизайну.

| Рівень | Змінних | Хибних слідів | Довжина ланцюжка |
|---|---|---|---|
| Junior Investigator | 4 | 0 | 3 |
| Middle Investigator | 6 | 1 | 4 |
| Senior Investigator | 8 | 3 | 5 |

## 8. Ігровий цикл

Стан сесії (`user_data["state"]`) — кінцевий автомат:

```
ASK_PASSWORD → MENU ⇄ WAITING_HYPOTHESIS
                    ⇄ WAITING_LEVEL_CHOICE
```

**Команди меню (`cmd`):**

| Команда | Дія |
|---|---|
| `start` / `меню` | Показати меню; пункт 5 підписаний «[Заблоковано]», якщо ранг Junior |
| `1` | Бриф справи: опис + легенда |
| `2` | Список аксіом |
| `3` | Перейти в `WAITING_HYPOTHESIS`, попросити ввести гіпотезу |
| `4` | Показати дерево виведення останньої перевірки |
| `5` | Обрати рівень наступної справи — **список рівнів залежить від рангу**: Junior не має доступу, Middle бачить 1–2, Senior — 1–3 |
| `6` | Зберегти профіль, завершити сесію на клієнті |

**Перевірка гіпотези (`WAITING_HYPOTHESIS`):**
- `PROVED` → `solved_count += 1`, `total_score += 10`, ранг перераховується, профіль зберігається.
- Інакше → `attempts_left -= 1`; ліміт спроб на сесію — 3 (`GameSession.attempts_left`), вичерпання лише попереджає, гру не блокує.

**Обмеження:** після успіху та повернення в меню (`start`) поточна справа **не змінюється автоматично**. Щоб отримати нову справу:
- гравець рангу Middle/Senior обирає рівень вручну (пункт 5);
- гравець рангу Junior має вийти і зайти знову — тоді при повторному логіні `get_starter_case(solved_count > 0)` кине помилку, і бекенд впаде на `generate_case(rank)`.

## 9. API

### `GET /`
Віддає `index.html`.

### `POST /api/command`

**Тіло запиту:**
```json
{ "command": "рядок команди", "username": "ім'я гравця" }
```

**Тіло відповіді:**
```json
{
  "result": "текст для термінала (може містити маркери [УСПІХ!], [ПОМИЛКА] тощо)",
  "rank": "поточний ранг або ''",
  "score": 0,
  "name": "ім'я гравця",
  "locked": false
}
```

Фронтенд розфарбовує `result` за ключовими словами (`[УСПІХ!]` → зелений, `[ПОМИЛКА]`/`[ВІДМОВА]`/`[УВАГА]` → червоний, заголовки меню → золотий). Якщо `locked: true`, поле вводу в браузері незворотно вимикається без перезавантаження сторінки.

## 10. Файлова структура

```
Investigation001/
├── app.py                  # Flask-сервер, увесь ігровий цикл
├── main.py                 # (застаріла CLI-точка входу, не використовується app.py)
├── cli.py                  # (застарілий CLI-інтерфейс, паралельний до app.py)
├── case_generator.py       # процедурна генерація справ
├── cases.py                # завантаження cases.json
├── game.py                 # GameSession: підготовка KB, перевірка гіпотези
├── player.py                # профіль, пароль, ранг
├── logic/
│   ├── models.py
│   ├── parser.py
│   ├── cnf.py
│   └── resolution.py
├── templates/
│   └── index.html          # для Flask render_template потрібен саме шлях templates/
├── data/
│   ├── cases.json          # стартова справа (id 404)
│   └── players.json        # профілі, паролі-хеші, статистика
└── README.md
```

> **Увага:** `render_template("index.html")` у Flask шукає файл у папці `templates/`. Якщо `index.html` лежить у корені проєкту (як на скріншотах Explorer), сервер поверне 500-ту помилку — перенесіть файл у `templates/index.html`.

## 11. Розбіжності з початковим дизайн-документом (README v3.0)

| У README | У коді |
|---|---|
| Режим «Злам» (мінімальна суперечлива підмножина) | Не реалізовано в грі. Функція `is_minimal_inconsistent` існує, але не викликається |
| Підказки (порівняти пару клауз / непарні літерали) | Відсутні повністю |
| Кампанія з 5 послідовних раундів + фінальний звіт | Відсутня; генерація нескінченна, прив'язана до рангу |
| Рівні: Новачок / Слідчий / Головний аналітик | У коді: Junior / Middle / Senior Investigator |
| Пункт меню «переглянути профіль і статистику» | Немає окремого пункту; ранг і бали видно лише в шапці термінала |
| — (не згадано) | Пароль з SHA-256, 3 спроби, перманентне блокування нікнейма |
| — (не згадано) | Вибір рівня наступної справи обмежений поточним рангом гравця |

## 12. Рекомендації

1. **Синхронізувати назви рівнів** — або перекласти назви рангів на українську і використовувати їх всюди (у `case_generator.py`, `player.py`, `app.py`), або оновити README англійською.
2. **Автоматична видача нової справи** після успіху для рангу Junior — зараз єдиний шлях це релогін, що не очевидно гравцю.
3. Якщо режим «Злам» потрібен — під нього вже готова логіка (`is_minimal_inconsistent`), бракує лише сценарію в `app.py` (новий стан `WAITING_SUSPECT_SET`, введення переліку номерів аксіом).
4. Розглянути легке обмеження на блокування (`locked_usernames`) — зараз воно знімається лише перезапуском сервера, що незручно для тестування.
5. Перевірити розташування `index.html` відносно `templates/` перед деплоєм.
